# 确定性引擎清单：非 AI 驱动的硬编码功能

> 版本：v0.4（整理稿）　　状态：可提交　　关联文档：`0.3.0-设计.md`、`0.3.1-交互式翻译流程设计.md`、`0.3.4-流程设计.md`、`0.3.8-方向设计.md`
>
> 本文回答两个问题：**① 项目里哪些功能是「非 AI 驱动」的硬编码/确定性逻辑（工具引擎）？② 哪些函数最容易在未来被改成 AI 驱动（提示词 / 视觉回流）？**
>
> 结论先行：**面向用户的决策尽量经 agent + 工具给出；纯确定性渲染/提取（列聚类、表格排版、缩放、OCR 框还原）仍是工具引擎，不宜也不应交给模型。** 本清单是该原则的落地索引，供审阅、取舍、防止「把确定性引擎误改回 AI」。

---

## 1. 判定标准（什么算「非 AI 驱动」）

一个函数属于**确定性硬编码**，当且仅当它**不调用 LLM / 视觉模型做决策**，其输出由输入与固定规则唯一决定。允许它：

- 由外部注入 `ocr_fn` / `judge_fn` / `client` 等**可插拔后端**（注入的到底是确定性还是模型，不改变函数本身的骨架是确定性编排）；
- 做成「喂给 AI 的确定性工具」，即工具**注册与绑定**（schema、参数、返回值）是确定性的。

判为**非**确定性（AI 驱动）的典型特征：内部构造 `OpenAI(...)`、组装 system/user prompt、走 `completion` / `chat/completions`、或把模型输出作为**决策来源**而非只是可插拔打分器。

## 4. AI-化风险标注（最容易被改成 AI 驱动的函数）

> 评估口径：**如果不加约束，哪个函数最可能被「用模型输出替代固定规则」？** 依据：主流 VLM/DocLayout 方向（见 `0.3.8-方向设计.md`）、本项目已有的 AI 化先例、以及「确定性工具层」设计原则。

### 🔴 高危（已存在 AI 路径，或外部方向已明确该走模型）

| 函数 | 现状 | 最可能的 AI-化形态 | 触发信号 |
|---|---|---|---|
| `classify_page` / `get_doc_info` / `detect_language` | M1 纯确定性分型 | VLM 逐页理解 / DocLayout 版面分型 | `0.3.8-semantic-parse.md`（B-④）已把语义化解析列为方向 |
| `build_structure` / `make_geometric_structure_fn` | 离线几何启发式 | DocLayout-YOLO/MinerU 语义结构（`0.3.8-semantic-parse`） | 已存在 `make_doclayout_structure_fn`（带降级） |
| `_parse_checks` / `_parse_scope` / `_base_from` / `compile_from_user`（规则分支） | 确定性规则解析 | AI 槽填充（`make_llm_flow_compiler` 已在运行时注入） | `compile_from_user(llm=...)` 本身就是默认 AI 分支，规则仅离线兜底 |
| `_classify_choice` / `_interpret_answer` / `interpret_decision` | 关键字 → 离散决策 | 用 LLM 直接解读用户/特殊页的自由文本回答 | 特殊页答案已在用 `make_llm_interpret`；「自由文本回答」是既定交互方向 |
| `parse_preview_command` / `_cn_to_int` | 正则识别整条预览导航命令 | LLM 意图解析（会侵蚀「整条命令才识别」的现语义） | 侧栏自由文本天然更适合模型解读 |

### 🟠 中危（有 AI-化空间，但有明确边界）

| 函数 | 现状 | 最可能的 AI-化形态 | 触发信号 |
|---|---|---|---|
| `_normalize_number` / `_repair_number_separators` | 规则修数字形状 | VLM OCR 直接返回干净数字（扫描报表是「最痛场景」，见 `0.3.8-formula-figure.md`） | DeepSeek-OCR 类 VLM 已对扫描件有实测收益 |
| `judge_pages`（软指标） | 确定性编排 + 注入 `judge_fn` | 完全交给 LLM-as-judge | `0.3.8-eval-harness.md`（A-②）把 LLM-as-judge 列为软指标；但 `measure_*` 硬指标**永不**为其覆盖 |
| `_estimate_skew_from_gray` / `_deskew_affine` / `detect_page_skew` | 图像处理 | 让模型「先否定后肯定」选择是否修正（`main_window` 已有该交互模式） | 已有 AI interpret 联动 |
| `_fit_block` / `_fit_one_line` / `_fit_exact_n` / `_rebalance_to_n` / `_compute_table_layout` | 确定性排版 | C-⑥ IR 自适应重排版（可能由模型生成排布，见 `0.3.8-ir-retypeset.md`） | 排版是「语言处理 vs 布局保真」张力点；但 CLAUDE.md 明确排版属工具层，不宜交给模型 |
| `_pick_translatable` / `_is_entry` / `_is_formula_block` | 规则判「是否需要翻译 / 是否公式」 | 模型判断是否漏译/公式占位 | 公式/图理解是 `0.3.8-formula-figure.md`（B-⑤）方向 |
| `_number_signature` / `_check_numbers` | 数值值域比较 | 多模态模型逐位比对 | 「数字一致性」是最需要防 AI 幻觉的项，建议保持确定性，AI 仅作二次复核 |

### 🟢 低危 / 已免疫（有充分理由保持确定性）

| 函数 | 理由 |
|---|---|
| `_wrap` / `_break_word` / `_break_latin_word` / `_num_atom` / `_draw_*` / `_is_vertical_label` | 纯几何/字形保真，模型给的字符级排版反而会错 |
| `extract_document_text` / `_order_*` / `_collect_*` / `group_by_page` | 提取与阅读序是「喂给模型的前提」，改 AI 会引入噪声 |
| `save_*` / `_export` / `_apply_overlay` | 导出一旦失真即全盘皆输，必须确定性 |
| `_reconstruct_ocr_grid` / `_merge_label_fragments` / `_cluster_ocr_*` | **已免疫**：AI 表格重建（`make_table_rebuild_fn` / `make_merge_tool_fn` / `verify_number`）曾存在并已被删除；保留确定性网格重建是验证过的选择 |
| `settings.py` / `doc_context.py` / `preview.py` 纯函数 / `sidebar.py` / `about_dialog.py` / `control.py` | 纯逻辑/状态/控件，无 AI 化意义 |
| `prompts.py` | 本身就是提示词原料，不存在「改成 AI」的问题 |

## 5. 变更守则

1. **不要把确定性引擎改回 AI**：`_draw_*` / `_wrap` / `_fit_*` / 表格网格 / 数字保护 / 提取阅读序，属工具引擎，理应交给 agent + 工具暴露而非模型直接跑。
2. **AI-化先过「审计门 + 降级」**：凡想把某个硬编码改为模型驱动，先给确定性兜底（如 `make_doclayout_structure_fn` 降级几何、`_get_ocr_engine` 降级跳过），且用 `_check_*` 确定性审计确认无回归。
3. **`_check_*` 必须保持确定性**：复核门是「先确定性跑、只对发现问题的页才交给 AI」；绝不能让「复核是否通过」反过来依赖模型。
4. **AI-化改动先写进 `docs/0.3.x` 方向稿**：参考 `0.3.8-semantic-parse.md` / `formula-figure.md` / `ir-retypeset.md` 的立项逻辑，再落地代码。
5. **数字一致性例外**：`_number_signature` / `_check_numbers` 保持确定性，AI 只作为二次复核，且**永不**覆盖 GDP、金额等关键值。

## 6. AI-化落点 vs 新增功能冲突（MCP / chat_tools / agent / eval）

> AI-化与 MCP、常驻对话、agent 编排、eval harness 等新增功能的冲突，本质只有两类：**「谁能调模型」** 与 **「确定性契约是否被破坏」**。只要 AI-化**套进既有注入点**、而不是写死进确定性核心，就能与这些功能共存。

### 6.1 注入点映射（AI-化唯一允许的入口）

| 注入点 | 对应功能 | 确定性默认 | 谁往里注入 AI |
|---|---|---|---|
| `translate_fn` | 翻译引擎（`make_ir_translate_fn` / `TranslationEngine`） | 无（本身就是 AI） | MCP / agent / IR 共用 |
| `ocr_fn` | OCR 后端 | `None` → RapidOCR（离线确定性） | agent / GUI 注入 VLM；**MCP 用 `ocr=False`** |
| `structure_fn` / `parser=` | 版面结构 | `parser="geo"`（确定性） | agent 注入 DocLayout-YOLO；**MCP 钉死 `parser="geo"`** |
| `judge_fn` | LLM-as-judge 软指标 | 无（`measure_*` 硬指标独立） | `eval_harness.py` 注入；`measure_*` 不依赖它 |
| `llm=` | 自由文本槽填充（`compile_from_user`） | `None` → 规则解析（确定性） | chat / agent 注入 AI |
| `client=` / `model` | 复用单一 OpenAI 连接池 | 自建 | 各调用点统一注入一个 client |
| `render_handler` / `image_provider` | 视觉反馈（`render_page` / `_image_url`） | 确定性渲染 | agent 注入 PNG |

**规则**：任何确定性函数要 AI-化，必须**新增或复用上述注入点并保留确定性兜底**；绝不允许在函数体内直接 `OpenAI(...)` / 拼 prompt。

### 6.2 各新增功能的冲突与解法

| 功能 | 冲突 | 解法 |
|---|---|---|
| **MCP**（`mcp.py`） | `get_doc_info` 显式 `ocr=False`、`get_structure` 硬编码 `parser="geo"`：AI-化分型/结构后会与 GUI 侧**两套真相**；headless 翻译若被 VLM OCR 拖入模型则**慢/缺模型即崩** | MCP 走注入点选确定性（`ocr_fn=None` / `parser="geo"`），VLM/DocLayout 只进 agent/GUI 侧 |
| **chat_tools**（`ChatSession` 工具循环） | 只读工具变 AI 会形成**模型→工具→模型 自环**；且混用 `interaction_*` 与翻译侧参数；tokens/cost 双倍，损 `_MAX_TOOL_ROUNDS` | 交互侧工具**保持确定性**，AI-化只发生在翻译/编排层 |
| **agent 编排**（`run_page_visual`） | agent 已逐页调模型，决策用确定性工具再变 AI → **递归 + 预算/参数**问题 | 工具保持确定性；AI-化仅作可选后端注入 |
| **审计门**（`_check_*`） | AI-化判定「是否通过」→ 复核没跑却放行 | 审核判定**必须确定性**；AI-化只接管「修复」 |
| **IR / eval**（`ir.py` / `eval.py`） | LLM-as-judge 若须必需则破「无模型可跑」；`measure_*` 硬指标被软指标覆盖 | `judge_fn` 可注入；`measure_*` 独立、**永不**被 judge 覆盖 |

### 6.3 必须从 chat_tools 显式「排除 AI-化」的工具

这些工具是交互模型的**只读数据源**（喂给模型的事实，而非另一次模型调用）。若被 AI-化，会同时触发「自环 + 参数集混淆」，因此**任何情况下都保持确定性**，只在被用作「AI 后端的注入目标」时例外（且此时绝不作为 chat 工具暴露）：

- `get_doc_info` / `classify_page` / `get_structure` / `get_table`（`chat_tools.py` / `agent/flow.py` 同名工具）
- `read_page` / `goto_page`（读页/导航，返回数据而非决策）
- `audit_page` / `self_check` / `_check_*`（审计结果必须确定性，chat 只读 findings）
- `get_settings` / `set_setting` / `re_export` / `run_translate`（状态/触发类，非 AI 决策）

> 对应「AI 工具有效铁律」：工具要么**有真实副作用**（`set_text` / `apply_annotation` / `retranslate` / `re_export`），要么**确定性返回数据**（上面的只读工具）；**绝无第三种**「调用工具时偷偷调模型」的形态。
