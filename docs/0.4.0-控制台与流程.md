# 0.4.0 单一控制主体：AI 控制台 + 流程

> 状态：已定型（方向）。
> 一句话：**AI 是唯一控制主体；对话是「控制台」，翻译是控制台授权后启动的一个「流程」。**

---

## 1. 三个误解的澄清

在谈"控制台 + 流程"前，先归位几个容易混的概念：

1. **模型只有一个。** 一个 `models.json` 模型（qwen3.8 / ds4-pro）是同一实例。
2. **"两个 AI"不是两个模型，而是两条循环 + 两套参数 + 两套工具表**：
   - 两条循环：`ChatSession`（对话）与 `DocumentSession`（翻译流水线）。
   - 两套参数：`interaction_*`（对话）与 `request_params()`（生产）。
   - 两套工具表：已由 `agent/tool_catalog.py` 的单一 `TOOL_CATALOG` + 受众过滤解决。
3. **"第二个控制器"的假象**来自内部那条逐页 agent 循环——但它是**有界执行引擎**（`max_steps_per_page` / `max_rounds`）+ **确定性审计门**（`audit_page`），不是会自己凭空做决定的平级主体。

## 2. 架构图

```
        用户
         │  一句话（自然语言）
         ▼
┌──────────────────────────────┐
│  AI 控制台（ChatSession/侧栏）  │ ← 唯一控制主体
│  · 与用户交互，确定流程与要求     │
│  · 调用「流程工具」              │
│  · 向用户汇报结果                │
└──────────────┬───────────────┘
               │ run_translate / run_flow / re_export
               ▼
┌──────────────────────────────┐
│  流程（DocumentSession + 逐页）  │ ← 被启动，不是平级控制器
│  · 有界逐页循环（max_rounds）    │
│  · 确定性审计门（audit_page）    │
│  · 调用确定性工具层              │
└──────────────┬───────────────┘
               │ 结果回到控制台
               ▼
         汇报给用户
```

## 3. 各部分落在哪（对照代码）

| 角色 | 代码 | 说明 |
|---|---|---|
| 唯一控制主体 = 控制台 | `chat.py` 的 `ChatSession` / `ChatWorker`（侧栏） | 用户入口；决定流程与要求；汇报 |
| 流程工具（控制台可调度） | `chat_tools.py` 的 `run_translate` / `run_flow` / `re_export` | 本质是"控制台授权后启动的一个流程" |
| 被启动的流程 | `agent/flow.py` 的 `DocumentSession`（+`run_flow` 骨架） | 不是平级控制器 |
| 有界执行引擎 | 逐页 `run_flow` → `FlowAgent.run(max_rounds=…)` | 每页 `max_steps_per_page=96` / `max_rounds` 硬上限 |
| 确定性审计门 | `agent/flow.py` 的 `audit_page` / `_ai_self_check`（`REVIEW_MAX_ATTEMPTS=3`） | 干净页直接跳过，只有 findings 才交给 AI 修正 |
| 单一工具来源 | `agent/tool_catalog.py` 的 `TOOL_CATALOG` | agent/chat 各自按 `audience` 过滤 |

## 4. 参数轴（同一模型，按调用目的调温）

**这个轴不是"交互 vs 非交互"，而是"控制台/对话" vs "流程/生产"。** 关键区分是"要不要自然度/变化"：

| 侧 | 参数 | 温度/推理 | 用途 |
|---|---|---|---|
| 控制台 / 对话 | `interaction_temperature` / `interaction_reasoning_effort` | 0.6 / medium | 侧栏自由对话（要自然、有变化） |
| 流程 / 生产 | `temperature` / `reasoning_effort`（`request_params()`） | 0.2 / low | 翻译、agent 逐页 decide、特殊页解读、预览、标注、导出（要稳、要便宜） |

注意：连"读用户意图"的调用（`make_llm_interpret`、`make_llm_flow_compiler`，把用户自由文本解析成 translate/keep/skip 或 FlowSpec JSON）也归**流程/生产侧**——它们要的是**确定性单次答案**（`temperature=0.0`、`max_tokens` 少），是"解析"不是"聊天"。真正要"有变化"的只有侧栏自由对话那一处。

## 5. 红线（边界上唯一要警惕的）

**别把整篇翻译塞进一条对话循环。** 整篇几百块、几十页塞进对话上下文会爆、也极慢。

正确的形状是：**控制台定义流程/要求 → 启动流程 → 流程用有界循环 + 确定性审计去跑 → 结果回到控制台 → 控制台汇报**。
- 控制台只负责"定夺 + 启动 + 汇报"；
- 逐块/逐页的机械执行交给有界流程；
- 数字/表格/版面这类"该确定的"绝不交给 AI 主观判断（`audit_page` / `_check_*` 保持确定性主判定）。

## 6. 入口唯一性（没有第二个控制器）

- `_start`（真正启动流水线）**只能经控制台到达**：按钮 → `_start_via_chat()` → 聊天 `run_translate` 工具 → `_start`。
- 没有绕过控制台直接启动 `DocumentSession` 的路径；拖放/命令行只设置源文件，不启动流水线。
- 因此"控制台"是唯一的控制主体，`DocumentSession` 只是它启动的一个流程/执行体。

## 7. 结论

- 控制和定夺收敛到**一个控制主体（对话控制台）**。
- 翻译、质检、导出都是**控制台可调度的"流程工具"**。
- 逐页执行是**有界执行引擎 + 确定性审计门**，不是第二个 AI。
- 工具表**单一来源**（`TOOL_CATALOG`）+ 受众过滤。
- **意图解读一分为二（合理的取舍，不是"两个 AI 读意图"）**：控制台对话用高温度（`interaction_*`，要自然）；流程内解读用户回答（`make_llm_interpret` 的 temp-0 分类、`_classify_choice` 关键字解析、`compile_from_user` 的槽填充）用低温度/确定性（要稳定单次答案）—— 前者是**对话**，后者是**解析**。文档以此为准，避免误以为控制台丢了意图权。

这一版"定型"只做了**把既有形状成文化 + 命名诚实化**（代码本身已是这个形状）。
