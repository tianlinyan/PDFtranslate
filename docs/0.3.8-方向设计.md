## 1. 调研结论（2025 年关键方向）

### 1.1 语义化「文档解析」取代纯几何/OCR 提取
主流工具不再只靠 `PyMuPDF get_text("blocks")` + OCR，而是先用**版面/结构模型**把 PDF 还原成有语义的文档模型（标题层级、段落、语义表格、图、公式、栏/页）。

- 代表：DocLayout-YOLO、MinerU、Docling、Marker。
- 参照：**PDFMathTranslate**（EMNLP 2025 demo）的流水线 = MinerU 提取 + DocLayout-YOLO 版面解析 + PyMuPDF 重排 + pdfminer.six 解析（[GitHub](https://github.com/aprilispp/PDFMathTranslate) / [arXiv 2507.03009](https://arxiv.org/abs/2507.03009)）。
- 底层：**[MinerU 2.5](https://github.com/opendatalab/MinerU)**、**[Docling](https://github.com/docling-project/docling)**，输出带结构的统一表示，支持「按章节/表格切块」而非盲目文本切片。

### 1.2 中间表示（IR）重排版——「解耦语义与几何」是最大架构演进
**BabelDOC**（[arXiv 2605.10845 / ACL demo 2026](https://huggingface.co/papers/2605.10845)，开源仓库 [funstory-ai/BabelDOC](https://github.com/funstory-ai/BabelDOC)）核心主张：把「视觉布局元数据」与「语义内容」**解耦**，翻译发生在 IR 上，做的是**文档级**操作（术语抽取、跨页上下文、glossary 约束、公式占位），最后用自适应排版引擎把译文**重锚定**回原版式。其 200 页基准 + 人工 + 多模态 LLM-as-judge 证明在**版式保真 / 视觉美观 / 术语一致性**上优于基线——直击「语言处理 vs 布局保真」的根本张力。

### 1.3 视觉语言模型（VLM）做 OCR/结构理解
新 VLM 直接在图上理解版面与文字，替代传统 OCR，且上下文更省。

- **DeepSeek-OCR**（[arXiv 2510.18234](https://huggingface.co/papers/2510.18234)）：用「光学 2D 映射」做上下文压缩，OmniDocBench 上 <800 vision tokens 超 MinerU2.0（每页 6000+ tokens），<10× 压缩率下 OCR 精度 97%、20× 仍约 60%。
- 其他：**[PaddleOCR-VL](https://aihub.caict.ac.cn/models/PaddlePaddle/PaddleOCR-VL-jz)**、[langparser](https://github.com/2812427914/langparser)。
- 对**扫描报表**（数字/表格线）尤其有价值——正是本项目最痛的场景。

### 1.4 生态化：MCP / Agent 集成
pdf2zh 已提供 `--mcp`/`--sse` 把翻译服务暴露给任意 AI agent（[pdf2zh MCP server](https://lobehub.com/mcp/lichman0405-pdftranslate-mcp)）；Immersive Translate / Document Translator 则做浏览器端双栏对照（[Immersive Translate/BabelDOC](https://similarlabs.com/zh/p/immersive-translate)、[Chrome 扩展](https://chromewebstore.google.com/detail/document-translator-trans/ekgbhhaimaahdlaiplkafkomhoblilel)）。

## 2. 现状与差距

### 2.1 优势（已领先同类开源工具）
本项目已是 **AI 为中心 + 人机协同** 的交互式工作台：agent 工具层、确定性审计（`audit_page` + 四类 `check_*`）、流程框架（`flow_steps` + `user_flows`）、常驻对话工具、预览导航/标注、`re_export`/overlay。这与 pdf2zh 这类「批处理 CLI」不是一个物种——**编排层面大幅领先**。

### 2.2 天花板主要在「内容理解保真」，而不是编排

| 差距 | 现状 | 影响 |
|---|---|---|
| **无语义文档模型** | 靠几何块 + RapidOCR（`extract_document_text` 的 `get_text("blocks")`） | 复杂文档（跨栏标题、语义跨页表格、图注、公式）解析上限低 |
| **公式不处理** | 未做公式占位 | 科学论文/数学内容会被改坏（PDFMathTranslate 的立身之本恰在此） |
| **逐块翻译丢上下文** | 块级翻译、缺跨页/跨栏语义注入 | 术语/人称跨页不一致、栏间错位 |
| **重排版仍是逐块回填几何** | 逐块按 bbox 绘制（`_draw_translated_block` / `_fit_band`） | 溢出/越线/行带问题虽已大量优化，但本质仍是「语言处理 vs 布局保真」的张力，不如 IR 结构性解决 |
| **缺质量/eval 基准** | 只有 `check_translation.py` 确定性自查 | 无法度量每次改进、难复现 |

## 3. 方向总览（三档、按优先级）

```
A 快速见效（1–2 周，低风险）
  ① MCP server 模式         —— 把翻译/重译/审计能力暴露给任意 AI agent
  ② 质量评估 harness        —— 译文保真 + 版式保真指标，作为回归基准
  ③ 工程与文档收尾          —— README/版本漂移修复、配置参数说明

B 内容理解升级（2–4 周，核心增值）
  ④ 语义化解析层            —— 可选解析后端，输出结构模型映射回扁平 blocks
  ⑤ 公式占位 + 图注/图理解  —— 解锁「科学论文/带公式文档」场景

C 架构级方向（4–8 周，payoff 最高）
  ⑥ 中间表示（IR）+ 重排版  —— 解耦语义与几何，结构性解决溢出/跨页/术语问题
  ⑦ 现代 OCR/结构模型升级   —— 扫描页从 RapidOCR 升级为 VLM OCR
```

**建议推进方式**：先做 **A-② 评估 harness**（动结构前先建立基准，让 B/C 每一步可度量）；再 **A-① MCP**（低成本扩大生态）；随后按 **B-④ → B-⑤ → C-⑥ → C-⑦** 顺序推进。

## 4. 各方向详述

### 4.1 档位 A · 快速见效

#### ① MCP server 模式
- **做什么**：新增 `--mcp` / `--sse` 启动模式（可参考 pdf2zh），把本项目的翻译/重译/重新导出/审计能力暴露为标准 MCP 工具；同时支持**上下文注入**（把 `WorkflowState` / `DocContext` 的当前状态作为会话上下文传给外部 agent）。
- **代码落点**：新增 `translate_app/mcp.py`（或用 `mcp` 库工具包）；在 `MainWindow` 之外提供无 GUI 入口（`main.py` 增加命令行分发）。工具描述复用 `AGENT_TOOL_DESCRIPTIONS` / `CHAT_TOOL_DESCRIPTIONS`，避免重复维护。
- **价值**：低投入、高杠杆，完全契合现有 AI 中心定位；让任意 agent（Claude/ChatGPT 桌面、IDE 插件、其他文档工作流）能调用本项目能力。
- **取舍**：会复制一份「无 GUI 会话」路径，需注意与 `worker` / `DocumentSession` 的状态同步；首版可先用**无头批处理**（翻译单文档）降低复杂度。
- **验证**：`test_mcp`：MCP 工具清单与绑定工具对齐；一次端到端（请求→翻译→返回 pdf）。

#### ② 质量评估 harness
- **做什么**：把现有的 `check_translation.py`（数字一致性/残留中文/章节编号/页数）从「自查」升级为「可度量改进的回归基准」：
  - **译文保真**：参考 BabelDOC 的 benchmark，用参考译文 + LLM-as-judge（多模态，看版式）给 0–100 分。
  - **版式保真**：新增确定性指标——块 bbox IoU（译文块 vs 原文块）、溢出/越线检测率、行带越界率、数字一致性率。这些指标现有代码**几乎都能算**（`_fit_band`、`_fit_block`、`check_numbers` 已有），只需聚合成报告。
- **代码落点**：新增 `translate_app/eval.py` 或沿用 `check_translation.py`（加 `--metric`）；产出 JSON/CSV，供 `verify_real_run.py` / `verify_selfcheck.py` 复用。
- **价值**：给 B/C 每一步改进提供客观可复现的度量，避免「改了就回归、回了又改」的无底洞。
- **验证**：`test_eval`：对样例页算出稳定指标；两次运行可复现。

#### ③ 工程与文档收尾
- **做什么**：修复 README 漂移（写 v0.3.2、只列 6 语言，实际已到 v0.3.7 并新增俄/日/韩）；补齐 `models.json` 的 `page_concurrency`/`concurrency`/`batch_size` 调优说明；若落地 MCP，补齐其使用文档。
- **代码落点**：`README.md`、`translate_app/__init__.py`、`docs/`。
- **验证**：纯文档，无测试。

### 4.2 档位 B · 内容理解升级

#### ④ 语义化解析层
- **做什么**：引入**可选**文档解析后端（在 Docling / MinerU / DocLayout-YOLO 中选一），输出带语义的结构模型（段落/标题层级/语义表格/图/公式/栏与页），并**映射回现有扁平 `blocks` 列表**（`Block` 扩展 `kind`/`level`/`table_ref` 等语义字段）。
- **代码落点**：`pdfio.py`（`extract_document_text` 增加可选解析后端路径）；`agent/tools.py` 的 `get_doc_info` / `classify_page` / `read_page` 消费新字段；`WorkflowState` / `DocInfo` / `PageTriage` 扩展。
- **开关与兜底**：用 `models.json` 条目或界面开关控制；**保留现有确定性几何路径为兜底**（符合项目「fail-closed / 降级」哲学）。解析后端为可选依赖（大模型/ONNX，未装则回退）。
- **价值**：立刻喂给 agent 与 `classify_page`/`get_doc_info`，让 AI「看懂结构」，而不是只看几何。
- **取舍**：新依赖体积大（ONNX/VLM）；必须保持「可回退」；注意与 OCR 路径的协调（扫描页仍走 OCR，文本页走解析后端）。
- **验证**：`test_pdfio`：后端输出映射到 `blocks` 后，`classify_page` 分型更准；后端未装时回退到现状。

#### ⑤ 公式占位 + 图注/图理解
- **做什么**：
  - **公式占位（formula placeholdering）**：识别公式区域（`classify_page` 增补 `formula` 分型），翻译时**占位、绝不改写**公式本体（BabelDOC 公式占位思路）。
  - **图注/图理解**：用 VLM 或现有 `render_page` 让 agent 看懂图与图注（`apply_annotation`/`read_page` 已具备此能力基础，只差「把图内容/图注作为上下文注入」）。
- **代码落点**：`pdfio.py`（`_is_formula_block` / 公式检测）、`translator` 或 `prompts`（公式占位规则）、`agent/tools.py`（图注工具）、`prompts.page_task`/`agent_tool_policy` 补公式/图注规则。
- **价值**：解锁「科学论文/带公式文档」这一 PDFMathTranslate 的立身场景，是当前最明显的功能空缺。
- **取舍**：公式识别精度是难点；可先从「保守占位（检测到疑似公式→整块保留原文、不触发改写）」做起，再逐步用 VLM 精确识别。
- **验证**：`test_pdfio`：含公式样例页被标记、公式块不翻译；真机样例对照。

### 4.3 档位 C · 架构级方向

#### ⑥ 中间表示（IR）+ 重排版
- **做什么**：借鉴 BabelDOC，把「语义内容」与「几何元数据/版面」解耦——解析 → **IR** → 翻译 IR → **自适应重排版**回原版式。IR 承载文档级操作：术语抽取、跨页上下文、glossary 约束、公式占位。
- **与现有代码关系**：**不是推翻 `pdfio.save_*`**，而是把「逐块翻译→回填 bbox」升级为「IR 翻译→重锚定」。IR 可作为流程间传递的数据，**天然融入已落地的 Flow 框架**（`ToolStep`/`AgentStep` 的输入/输出可改为 IR 片段）。
- **代码落点**：新增 `translate_app/ir.py`（IR 模型 + 解析/序列化 + 重排版引擎）；`pdfio.py` 的 `save_*` 改为消费 IR；`agent/flow` 的 `translate_page` / `self_check_page` 适配 IR。
- **价值**：结构性解决当前最难的三个问题——**溢出/越线、跨栏/跨页语义一致性、术语一致性**（BabelDOC 数据支持）。
- **取舍**：**这是最大的改动**，涉及解析、翻译、排版、导出全链路；必须分阶段、且以 A-② 的基准持续度量。**建议先做 IR 的「解析 + 术语/跨页上下文 + 表格」子集，跑通科学论文场景，再扩展到全类型。**
- **验证**：`test_ir`：IR 往返无损；跨页/跨栏一致性（术语、人称）明显优于块级；版式保真指标不劣化。

#### ⑦ 现代 OCR / 结构模型升级
- **做什么**：扫描页（本项目最痛场景）从 RapidOCR 升级/增强为 VLM OCR（DeepSeek-OCR / PaddleOCR-VL 之一），利用其「上下文压缩」降低长扫描文档的 token 成本，并提升扫描表格数字/线格的识别保真。
- **代码落点**：`pdfio.py` 的 `_get_ocr_engine` / `_ocr_page_blocks`；`_OCR_CACHE_VERSION` 递增（字段语义变化必须递增，见 CLAUDE.md 铁律）。
- **价值**：破解扫描报表的数字/表格线保真瓶颈（现有已到物理极限，见 v0.3.x 真机实测）。
- **取舍**：VLM OCR 依赖更大（GPU/API），需保留 RapidOCR 为兜底；注意 token 成本（DeepSeek-OCR 的压缩正适合此）。
- **验证**：`test_ocr`：扫描报表样例数字一致性率提升；缓存与降级路径回归。

## 6. 未决问题 / 后续

- **IR 的选型与范围**：IR 模型是自己定义还是参考 BabelDOC 的 HTML/结构化表示？首版是否只覆盖「科学论文/公式/跨页表格」子集？
- **语义解析后端选型**：Docling / MinerU / DocLayout-YOLO 的取舍（依赖体积、GPU 需求、中文年报适配度、与扫描页 OCR 路径的协调）。
- **VLM OCR 的形态**：是**本地**（DeepSeek-OCR 类，需 GPU）还是**云端 API**（PaddleOCR-VL）？本地需确认与现有 llama.cpp 服务端并存；云端则进入 `models.json` 的端点配置体系。
- **MCP 的无头会话**：无 GUI 会话与 `DocumentSession` / `worker` 的状态同步方式（复用现有 `run_flow` 还是另建轻量入口）。
- **公式占位的保守/精确边界**：先保守占位还是直接 VLM 精确识别，决定实现复杂度与准确率。
- **README 语言清单**：README 与实际支持语种（含俄/日/韩）是否需忠实更新，避免「文档与实现不一致」。
